# Verification results (2026-10-05)

Four checks run before the build, each in headless Chromium 141 / Node 22 inside the build container. Full reports are summarized here; DESIGN.md carries the decisions that follow from them.

## Exact solver (HiGHS WebAssembly)

The exact MIP solver HiGHS runs inside a page opened by double-click from file://. I tested this in headless Chromium 141: the npm package highs@1.15.3 (HiGHS 1.15.1) runs in a Blob-URL Web Worker, with the wasm inlined as gzip+base64 and inflated in the worker with DecompressionStream. The solver adds about 1.8 MB to the HTML file. One documented option does not work: highs-js 1.15.3 ignores its own `wasmBinary` and `wasmModule` loader options (tested in Node and Chromium). Load the wasm through Emscripten's `instantiateWasm` hook instead. The test model has 20 stops, which became 29 delivery tasks (788 rows, 2,107 columns, 2,020 binaries). HiGHS never proved optimality on it. Seed 1 cold gave 12,741.8 at 10 s (gap 23.5%), 12,045.2 at 60 s (gap 19.0%) and 10,634.8 at 300 s (gap 7.87%), with identical results in Node and the browser. A simple simulated-annealing heuristic running in a Blob worker found 10,380 in about 2 s, better than the 300 s MIP result. Fed that plan as a warm start, HiGHS accepted it at once and proved it is within 6.4% of optimal in 60 s. So the MIP's real value in the product is the proven gap, not a better plan. CPU-heavy JS in a Blob worker posts progress, leaves the page responsive and stops at once on terminate(). Cancelling therefore means terminate() plus keeping the last plan the worker posted.

### Recommended approach

PACKAGING (tested in headless Chromium 141 from file://):
- Pin npm `highs@1.15.3` (HiGHS 1.15.1, single-threaded wasm).
- Put node_modules/highs/build/highs.js (168,432 B) verbatim into `<script type="text/plain" id="highs-js">`. It contains no "</script" or "<!--". Assert this in the build script.
- Put highs.wasm (3,531,385 B), compressed with gzip -9 and base64-encoded (1,625,816 B), into `<script type="text/plain" id="highs-wasm-gz">`. Plain base64 would be 4,708,516 B.
- Example: dist/minimal-solver.html is 1,947,680 B in total, including a 147 KB LP model.

WORKER (see minimal-template.html):
- `const code = $('highs-js').textContent + "\n;(" + workerMain.toString() + ")();"`
- `new Worker(URL.createObjectURL(new Blob([code], {type:'text/javascript'})))`
- Post `{type:'init', wasmGzB64: text}`.
- Inside workerMain:
  - Decode: `atob` → Uint8Array → `new Blob([gz]).stream().pipeThrough(new DecompressionStream('gzip'))` → `new Response(...).arrayBuffer()`.
  - Then `highs = await Module({ instantiateWasm(imports, receive){ WebAssembly.instantiate(bytes, imports).then(r => receive(r.instance)); return {}; } })`.
  - Do not use `{wasmBinary}` or `{wasmModule}`: 1.15.3 ignores them and tries to load highs.wasm next to the page, which file:// blocks.
  - Measured: decode 60-151 ms, instantiate 48-71 ms.

SOLVE (persistent API):
- `const model = highs.createModel({format:'lp', data: lpText})` (LP parse ~116 ms for 147 KB).
- `model.options.set({output_flag:false, time_limit: secs, mip_rel_gap: 1e-4})`.
- Read column names with `model.getColName(i)` for i in 0..`getDimensions().numCols`. HiGHS orders LP-format columns by first appearance, not by your generation order.
- Optional MIP start, either:
  - dense: `model.setSolution({colValue: Float64Array in HiGHS column order})`
  - sparse: `model.setSolution({indices, values})`. Giving only the binaries works; HiGHS fills in the continuous variables.
- `const C = highs.constants.callbackType;` then `model.run({ [C.mipImprovingSolution](ev){ postMessage({obj: ev.data.objective_function_value, gap: ev.data.mip_gap, bound: ev.data.mip_dual_bound, t: ev.data.running_time, x: ev.data.mip_solution}) }, [C.mipInterrupt](ev){ /* throttled progress; ev.interrupt() for custom stop rules */ } })`.
  - Use mipInterrupt for progress, not mipLogging. mipLogging only fires when output_flag=true.
- Afterwards:
  - `model.getModelStatus()`: 7 = Optimal, 13 = Time limit reached.
  - `Number(model.info.get('primal_solution_status')) === 2` means an incumbent exists; read it with `model.getSolution().colValue`.
  - `model.info.get('mip_gap')`, `model.info.get('mip_dual_bound')`, `model.getObjectiveValue()`, `model.getRunTime()`.
  - Always call `model.dispose()`.
- The legacy `highs.solve(lp, {time_limit})` also returns the incumbent at the time limit (Status 'Time limit reached', ObjectiveValue, Columns[name].Primal) but no gap.

CANCEL:
- `run()` blocks the worker, and SharedArrayBuffer does not exist on file:// (crossOriginIsolated=false), so the page cannot signal into a running solve.
- Instead, post every incumbent as it is found and call `worker.terminate()`; keep the last posted incumbent. Tested: the decoded plan from it matches its objective exactly.

FALLBACK:
- If `new Worker(blobUrl)` throws, inject highs.js with a script element whose textContent is the source, and call `Module({instantiateWasm…})` on the main thread. Tested: 36-44 ms to instantiate. The UI freezes for the whole solve.

SOLVER STRATEGY FOR THE PRODUCT:
- Run the heuristics in Blob workers first. The SA in heuristic-sa.js runs about 2.5-3.7 M moves/s and reached within 1-3% of the best value in 1-2 s.
- Seed HiGHS with the best heuristic plan, then show the "Exact MIP" result as best plan + proven gap. Example: seed 1 gives 10,409 at 6.4% gap after 60 s.
- Expect 'Time limit reached', not 'Optimal', at 20 stops / 29 tasks with this formulation.
- Never pass the `threads` option: the legacy solve aborts, and the persistent API throws HighsUnsupportedOptionError.

### Risks and unknowns

- Only Chromium (headless 141) was available here. Blob-URL workers, instantiateWasm and DecompressionStream from file:// in Firefox and Safari (desktop and iOS) were NOT tested. Keep the main-thread fallback (tested in Chromium) and a plain-base64 path for browsers without DecompressionStream; the plain-base64 path adds about 3.1 MB.
- Opening a local .html on iPhone/iPad (Files app or Quick Look) may not run JavaScript at all (inferred, untested). Phone use of the solver probably needs the planned hosted PWA, or should be limited to the planner laptop.
- The 3-index big-M time formulation has a weak LP bound. At 20 stops / 29 tasks HiGHS stays at 6-50% gap after 60-300 s and never reached 'Optimal'. Do not promise a proven optimum; show best plan + gap. A stronger exact model (e.g. set partitioning / column generation) would be needed for proofs, and that is a much bigger build.
- The full product model (rally-point selection, split/partial deliveries, time-of-day speed and risk factors, closed zones) is larger and partly nonlinear. The MIP will grow considerably and needs linearization or fixed-in-advance parameters. Its solve times are unmeasured.
- Each new highs-js version must be re-checked: in 1.15.3 the README/types document wasmBinary/wasmModule, but the build ignores them. Pin the exact version and keep the instantiateWasm hook.
- Wasm memory reached about 158 MB on this model. It may grow with larger models, and several parallel workers (compare mode) multiply it. Running several workers in parallel in the browser was not tested; it is inferred to work, with 4 cores reported here.
- Cancel by terminate() loses anything not already posted. Incumbents must be streamed (about 17 KB per incumbent for 2,107 columns), and the next solve needs a fresh worker plus wasm init (about 130-220 ms).
- The heuristic in heuristic-sa.js is a quick prototype (single-thread SA with relocate, pool-exchange, swap and 2-opt moves) built to judge MIP quality. It has not been tuned or tested on other instance families. Tabu search and ant colony were not built.
- Timing runs partly overlapped with other runs on the 4-core container (each solve is single-threaded). Node and browser incumbent timestamps still agreed within about 2%.

## Map, symbols and grid references

All three libraries can be inlined into one HTML file, and it works from file:// in headless Chromium with every network request blocked. The demo is 1,056,884 bytes (261,594 gzipped) and shows Leaflet 1.9.4, a Natural Earth outline of Taiwan plus Penghu, 2525 symbols drawn by milsymbol 3.0.4, MGRS in popups and a Leaflet default marker loaded from a data URI. There were zero page errors and zero non-tile external requests. OpenStreetMap tiles are the primary layer, with the coastline drawn underneath them. If tiles fail, the app removes the tile layer and shows the outline; this was tested for: browser offline, network unreachable, HTTP 403 text, and HTTP 403 with an image body. The last case fires Leaflet's 'tileload' event, not 'tileerror', so a fetch() check of one tile was added to catch it. The biggest risk found: tile requests from a file:// page carry no Referer header (measured), and OSM's tile policy requires one, so OSM may block tiles when the file is opened by double-click. Hosting over https (the planned PWA on GitHub Pages) avoids this. All SIDCs below passed milsymbol's isValid(), and I checked each rendered symbol visually in PNG screenshots.

Real OSM was unreachable from this container, so whether OSM actually blocks these requests is unknown. Hosting over https (the planned GitHub Pages PWA) sends a Referer and avoids the problem.
- Blocked-tile detection: a 403 that carries an image body fires 'tileload', not 'tileerror' (measured), so the fetch() check of the centre tile is what catches it. That check can read the status from a file:// page (origin 'null') only if OSM sends Access-Control-Allow-Origin, which I could not verify. In the Playwright simulation the status was readable even without that header, probably because the simulation skips the cross-origin check, so the simulation is not evidence either way. If the status is unreadable, the code treats the check as inconclusive and relies on tile events.
- OSM forbids offline use and prefetching of tile.openstreetmap.org tiles, so a future PWA must not pre-cache OSM tiles. The Natural Earth outline is the only offline base map: no roads or towns, and it looks blocky beyond about zoom 11 (source grid roughly 360 m x 190 m).
- The extract keeps only the main island and Penghu. Kinmen, Green Island, Orchid Island and the Chiayi sandbar were dropped; Matsu is not in the data at all. Changing the filter in extract-taiwan.js brings the others back.
- Hub symbol: 2525D has no supply-installation entity. The installation look comes from milsymbol's 2525E frame-shape digit (character 23 = '5'), taken from milsymbol's source and not checked against the 2525E text, or from the 2525C code SFGPUSS---H----. The plain supply unit 10031000001634000000 is the conservative alternative; the client should pick one.
- For 'mounted' platoons, the app must choose mechanized/tracked (121102) or motorized/wheeled (121104), per platoon or as one default. Whether to put '1/B/3-21IN' entirely in field T or split it into T '1/B' and M '3-21IN' is a convention choice; I inferred it rather than checking FM 1-02.2.
- milsymbol is 82% of the inlined size (862 KB). A custom ES-module bundle with only the 2525D land unit, land equipment and control-measure modules (the pattern documented in milsymbol's index.mjs) would likely be much smaller, but it needs a bundler such as esbuild and was not tested here.
- Only Chromium (headless, Playwright 1.56.1) was tested. Firefox and Safari file:// behaviour (fetch from origin null, data-URI CSS) was not tested.
- The inlined leaflet.js and milsymbol.js keep their two sourceMappingURL comments. They are harmless (only DevTools reads them, and no request was seen) but could be stripped.
- package.json uses ^ ranges; package-lock.json pins the tested versions (leaflet 1.9.4, milsymbol 3.0.4, mgrs 2.2.0, world-atlas 2.0.2, topojson-client 3.1.0). The builder should pin exact versions.

## Road geometry for Taiwan

Real road geometry for Taiwan can be embedded in the single HTML file, and routing on it was tested and works offline from file://. ## Google travel times and map/routing terms

Technically this is easy and free. Use the Routes API computeRouteMatrix, not the legacy Distance Matrix API, which new Cloud projects can no longer enable. A 50x50 run with TRAFFIC_UNAWARE is 2,500 elements in 4 requests. It bills the Essentials SKU, which has 10,000 free elements a month, so the first run and three re-runs each month cost $0; any further full run in that month costs $12.50. However, Google's current terms forbid what the spec plans to do. GMP Terms 3.2.3(b) forbids caching unless the Service Specific Terms allow it, and the Routes API section (19.3) only allows latitude/longitude for up to 30 days, so durations and distances cannot be stored or embedded at all. 3.2.3(a)(ii) also names bulk downloading of "distance matrix results", and Routes section 19.2 plus 3.2.3(e) bar using Routes content with a non-Google map, which includes our OpenStreetMap view. I wrote the requested Python script and validated it with 21 passing tests (mocked HTTP plus a local fake server). It has not been run against Google, and I recommend not embedding its output. Instead, build the matrix and road paths from OpenStreetMap data with OSRM, whose license allows storing results with attribution. Also, tile.openstreetmap.org blocks pages opened by double-click (file://) because they send no Referer, so the map needs a hosted URL or a fallback.

### Recommended approach

GOOGLE CALL (if used at all): POST https://routes.googleapis.com/distanceMatrix/v2:computeRouteMatrix with headers Content-Type: application/json, X-Goog-Api-Key: $GOOGLE_MAPS_API_KEY, X-Goog-FieldMask: originIndex,destinationIndex,duration,distanceMeters,status,condition (a field mask is required). Body: {"origins":[{"waypoint":{"location":{"latLng":{"latitude":..,"longitude":..}}}}...],"destinations":[same],"travelMode":"DRIVE","routingPreference":"TRAFFIC_UNAWARE"}. Limits: origins x destinations <= 625 per request (100 for TRAFFIC_AWARE_OPTIMAL or TRANSIT), at most 50 origins+destinations given as address/placeId (use latLng to avoid this), 3,000 elements per minute. 50 points = 4 blocks of 25x25 = 2,500 elements, all within one minute. SKU: Compute Route Matrix Essentials (no Pro features) has 10,000 free elements a month, then $5.00 per 1,000. TRAFFIC_AWARE moves it to Pro: 5,000 free, then $10.00 per 1,000. The REST response is a JSON array in no guaranteed order. Errors also arrive as [{"error":{...}}] (seen here). proto3 may leave out zero-valued fields.

SCRIPT: <build scratch>/verify-google/fetch_google_matrix.py (standard library only, Python 3.8+). Usage: `export GOOGLE_MAPS_API_KEY=...; python3 fetch_google_matrix.py --grid grid.json --dry-run` prints the plan and estimated cost without calling anything. Then `python3 fetch_google_matrix.py --grid grid.json --out google_matrix.json`.
- Output: {ids, minutes[i][j] (float, 2 decimals, directed i->j), meters[i][j] (int), source:"google", fetched_at:"YYYY-MM-DDTHH:MM:SSZ", meta:{...}}.
- meta holds routingPreference, blocks, http_requests, elements_sent, unreachable (id pairs), element_errors and a note.
- A ROUTE_NOT_FOUND pair is null in both matrices. The diagonal is 0. The minutes are raw Google times; the app applies the 1.5 convoy factor.
- Behaviour:
  - Blocks are planned so each request has <= 625 elements.
  - A rolling 3,000-elements-per-minute limiter is applied.
  - 408/429/5xx and network errors are retried with exponential backoff, honouring Retry-After.
  - Other 4xx errors (bad key, no key) fail at once.
  - Transient per-element errors or missing elements trigger a re-request of only the affected origins x destinations, so the whole block is not billed again.
  - A safety cap (default 10,000 elements) needs --allow-over-cap to exceed.
  - The output is written atomically and never contains the key. A missing key exits with code 2.
- Tests: <build scratch>/verify-google/test_fetch_google_matrix.py. Run it with `python3 -m unittest -v test_fetch_google_matrix.py` from that directory: 21 tests, all OK in about 1 s. The tests use the real 403/400 error bodies recorded from routes.googleapis.com.

### Risks and unknowns

- The spec's plan to embed a Google matrix permanently ('one-time script ... matrix embedded in the app') conflicts with the terms as written: 3.2.3(a)/(b), Routes section 19.3 and section 19.2/3.2.3(e) on non-Google maps. Aidan and the client should decide before anyone runs the script. This is my reading of the terms, not legal advice. An enterprise or government agreement between Google and the user's organization could differ, and I have not seen one.
- High Risk Activities / ITAR clause (3.2.1(c)): a military resupply planner, even with fictional data, could be seen as covered if it ever moved toward operational use. Worth flagging to the client.
- The pricing, SKU and developers.google.com policy pages were read through the WebFetch summarizer, because developers.google.com is not curl-reachable from this container. The numbers matched across two fetches but are not byte-verbatim. The cloud.google.com terms quotes ARE verbatim (downloaded HTML).
- Not confirmed: whether the 50 diagonal elements (origin == destination), ROUTE_NOT_FOUND elements or element-level errors are billed. 'Each element returned' suggests they are. The diagonal adds only 50 of 2,500 elements.
- The free cap appears to be per billing account per SKU per month (inferred from 'free monthly usage threshold for each Core Services SKU'). Other projects on the same billing account would share it.
- The script has never been run against the real API with a key (as instructed). Response parsing follows the documented examples, plus handling for omitted zero-valued fields. Only the real error shapes (403/400) were observed live.
- On macOS python.org builds, urllib HTTPS can fail with CERTIFICATE_VERIFY_FAILED until 'Install Certificates.command' is run. Setting SSL_CERT_FILE also works.
- A file:// build cannot show tile.openstreetmap.org tiles, because it sends no Referer (tested) and OSM blocks that (documented). Leaflet's referrerPolicy option cannot create a Referer for a file:// origin; that part is inferred, since only the default policy was tested. The double-click requirement needs a non-OSM tile source, a hosted URL, or an inline vector outline of Taiwan as fallback.
- OSRM alternative: the FOSSGIS demo server allows at most 1 request per second, non-commercial use, with no guarantees. Its table-size limit is unknown, and roughly 2,450 polyline calls may count as 'heavy usage'. Self-hosting OSRM with a Taiwan extract is safer but needs Docker and a Geofabrik download on Aidan's machine. Geofabrik and OSRM are not reachable from this container, so this was not tested here.
- OSRM times use OSM speed profiles and will differ from Google's. The 1.5 convoy factor and calibration should be re-checked if the source switches to OSRM.
